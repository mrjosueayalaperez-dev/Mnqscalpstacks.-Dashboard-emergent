# RCA — MNQ Scalp Stacks: production login loop

**Deployment:** mnq-scalp-stack (fastapi_react_mongo_shadcn — farm template, **Cloudflare frontend**)
**Live run:** `b46140f8-b622-41ac-ba72-903de7ab66e3` (redeploy, trigger=agentic) — **deployed 2026-09-20 21:59 UTC** (the most recent successful run; investigated ~2.5h later)
**Symptom:** a user logs in on the live site (https://mnq-scalp-stack.emergent.host) and is bounced back to the login page repeatedly.

---

## Verdict (short)
This is **NOT** a backend, cookie, CORS, or database bug. The backend on the live run is current and healthy, and the same code path works in preview. The failure is a **frontend/backend version mismatch at the Cloudflare edge**: the frontend currently *served* to users does **not** issue the email/password login request that the current source (working in preview) makes. So the app loads → calls `/api/auth/me` → 401 → routes to the login screen → the login UI never actually POSTs to `/api/auth/login` → user lands back on login = the loop.

A fresh redeploy is **likely to fix it**, with one caveat I could not verify from this toolset (Cloudflare KV/R2 — see "Would a redeploy fix it").

---

## Evidence

### 1. Backend is current and correct (not a stale backend)
Read directly from the live run's deployed source (`backend/auth.py`, `backend/server.py`):
- `auth.py` implements the full email/password JWT flow: `POST /auth/register`, `POST /auth/login`, `GET /auth/me`, plus Google `POST /auth/session`.
- `/auth/login` and `/auth/register` set an `access_token` cookie: `httponly=True, secure=True, samesite="none", path="/", max_age=3600` (+ `refresh_token`).
- `/auth/me` → `get_current_user()` reads the `access_token` cookie (or `Authorization: Bearer`), decodes it with `JWT_SECRET`, and 401s ("Not authenticated") when there is no valid cookie — which is the correct response for an unauthenticated request.
- `server.py` mounts the router (`api_router.include_router(auth_module.build_auth_router(db))`), so `/api/auth/*` is live.

### 2. Users are same-origin with the API (rules out CORS)
- `REACT_APP_BACKEND_URL` is baked as `https://mnq-scalp-stack.emergent.host` (confirmed both by the secret store `matches_expected=true` and Cloud Build log line 412: `REACT_APP_BACKEND_URL=https://mnq-scalp-stack.emergent.host`).
- Both custom domains (`mnqscalpstacks.com`, `www.mnqscalpstacks.com`) are **unverified and do NOT resolve** ("A records do not point to expected IPs"), so users are on `emergent.host`. Page origin == API origin == `mnq-scalp-stack.emergent.host` → **same-origin, no CORS involved.**
- Note for future: `CORS_ORIGINS="*"` with `allow_credentials=True` in `server.py` IS an invalid combo for *cross-origin* credentialed calls (browsers reject `Access-Control-Allow-Origin: *` with credentials). It is harmless today because traffic is same-origin, but it will bite if/when the custom domain goes live (page on `mnqscalpstacks.com`, API on `emergent.host` → cross-origin). Recommend setting `CORS_ORIGINS` to the explicit origin(s) before the custom domain is activated.

### 3. Same-origin POSTs to the backend SUCCEED (rules out edge/ingress blocking writes, and cookie-transport as the active fault)
In the post-deploy window (00:00–00:25 UTC), from the same active client IP `136.68.30.50`:
- `POST /api/subscribers` → 200
- `POST /api/backtests/seed-demo` → 200
- `PATCH /api/welcome/<id>/complete` → 200
- `POST /api/analytics/visit` / `heartbeat` → 200
- `GET /api/proof/*`, `GET /api/welcome/*` → 200

So writes reach the backend fine over the Cloudflare `/api/*` proxy.

### 4. The login endpoint is NEVER called (the smoking gun)
- Across the last **24h**, filtering specifically for `POST /api/auth/login|register|session`: **0 requests.**
- Meanwhile `GET /api/auth/me` returns **401 repeatedly**, both before and after the 21:59 deploy, from the actively-clicking user.
- Conclusion: the live user's browser calls `/api/auth/me` (on page load / route guard) but **never issues the login POST**. Since same-origin POSTs demonstrably work (§3), the request is simply not being made by the served UI — i.e., the served frontend does not exercise the current email/password login endpoints.

### 5. Login worked historically → cookie transport through Cloudflare is fine
- Both existing users (`operator@mnqscalpstacks.com`, `mr.josueayalaperez@gmail.com`, both role=admin) have `last_login` = **2026-09-19** (08:50 and 22:26 UTC). `last_login` is updated by the email/password `/auth/login` path (which creates no session doc), so email/password login succeeded as recently as Sep 19 — i.e., the `access_token` cookie set by the backend DID round-trip through the Cloudflare edge and authenticate. This weakens any "edge strips Set-Cookie" theory and points at a change in what the *frontend* does, appearing around/after the two Sep-20 redeploys.

### 6. Database is healthy (rules out DB binding / session persistence)
- `mongo_query` on the live run resolves DB `mnq-scalp-stack-test_database`, 18 collections, reads succeed.
- `users`: 2 docs (both admins, newest created 2026-08-13) — **no new user rows**, consistent with registration never completing in prod.
- `user_sessions`: newest 2026-08-30 (Google-session tokens only; email/pw login uses stateless JWT and writes no row here) — so its staleness is expected, not a fault.
- `login_attempts`: empty — the email/pw lockout counter has never been touched in prod, consistent with the email/pw login path never being exercised there.
- All secrets present and non-empty for auth: `JWT_SECRET`, `MONGO_URL`, `DB_NAME`, `REACT_APP_BACKEND_URL`, `CORS_ORIGINS`. (Only `STRIPE_LIVE_*` are empty — unrelated to auth.)

---

## Root cause
**Frontend/backend version skew on the Cloudflare-served frontend.** The backend and the freshly-built R2 assets for run `b46140f8` are current (source posts to `/api/auth/login`), but the frontend actually being served to users does not issue that request — so authentication can never establish a session, `/api/auth/me` stays 401, and the SPA bounces the user back to login. Everything else (same-origin writes, cookies, JWT, DB) is healthy.

## Why preview works but production doesn't
Preview always serves the current frontend bundle built from current source, whose `AuthContext.js` does `axios.post('/api/auth/login', … {withCredentials:true})` → 200 → `access_token` cookie set → `/api/auth/me` 200 → dashboard. Production is serving a frontend bundle that is out of sync with the current source, so that working code path is never invoked at the edge.

## Would a fresh redeploy of the current code fix it?
**Most likely YES.** A clean redeploy rebuilds the frontend from current source, republishes it to R2, and flips the Cloudflare KV version pointer (+ cache purge) so the current login UI goes live. Because same-origin POSTs already work (§3) and the cookie/JWT path has worked historically (§5), once the current frontend is actually served, login should succeed.

**Caveat / what I could NOT verify:** this toolset has no access to Cloudflare KV/R2, so I could not directly confirm which frontend bundle the edge is serving — the "stale served frontend" conclusion is a strong inference from the traffic pattern (§3–§4), not a direct read of the edge. If a clean redeploy does **not** change the behavior, the problem is the Cloudflare frontend go-live (version-pointer / cache) rather than app code, and needs platform/edge attention.

## Recommended actions
1. **Redeploy the current code** (fresh build so the frontend is rebuilt and republished).
2. **Verify after deploy** by reproducing a login and watching backend logs for:
   - `POST /api/auth/login` → **200** (proves the current login UI is now live and reaching the backend), followed by
   - `GET /api/auth/me` → **200** (proves the `access_token` cookie round-trips and authenticates).
   Also confirm a new row appears in `users` after a fresh registration.
3. If, after a clean redeploy, you still see `GET /api/auth/me` 401 with **no** `POST /api/auth/login` — escalate as a Cloudflare frontend version-pointer/cache issue (edge serving a stale bundle), not an app bug.
4. **Before activating the custom domain** `mnqscalpstacks.com`: change `CORS_ORIGINS` from `*` to the explicit origin(s), because `*` + credentials will break cross-origin login once page and API live on different hosts (§2).
